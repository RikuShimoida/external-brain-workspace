# ツイート下書き生成・投稿スキル（承認制）

X の過去ツイートと Evernote のノートという2つの「外部脳」を参照し、
**オーナーの価値観・人格が伝わる「有益なツイート」の下書き**を生成する。
そして**必ずオーナーの承認を得てから** X に投稿する。

狙いは、Podcast → note → X の流入導線のフックになるツイートを、
オーナーの時間を使わずに量産すること（背景は Issue #3、および
[references/tweet-criteria.md](references/tweet-criteria.md) 参照）。

過去の投稿・ノートから「人格のルーツになる言葉」を拾う部分は、既存の
`podcast-neta` スキルと発掘資産（`extract_tweets.py` / `podcast-idea-miner`）を
そのまま流用する。このスキルはその発掘結果を **投稿できるツイートの形に整え、
承認して投稿する** ところに責任を持つ。

## 大方針（CLAUDE.md と一致）

- **完全自動投稿はしない。** 下書きを提案 → オーナーが承認 → 投稿、が絶対のフロー。
  `mcp__twitter__post_tweet` を呼ぶのは、オーナーが投稿対象を明示的に選んだ後だけ。
- **捏造しない。** 各下書きは必ず**実在する投稿/ノートの引用**に紐づける。事実を作らない。
  過去の自分が言っていないことを、言ったかのように書かない。
- **勝手に突き進まない。** 探索範囲・生成件数・投稿の各チェックポイントで一声かける。
- **一度に浴びせない。** 提案は一度に大量に出さず、数件ずつに絞る（オーナーの特性）。
- 重い走査は `podcast-idea-miner` サブエージェントに隔離し、本体コンテキストを汚さない。

## 手順

### 0. 前提確認
- 作業ディレクトリは repo ルート（`external-brain-workspace`）想定。
- X アーカイブが `twitter-archive/extracted/data/tweets.js` にあることを確認する。
  無ければオーナーにアーカイブの場所を尋ねる。
- 投稿に使う `twitter` MCP が connected か確認する（`/mcp`）。
  未接続でも「下書き生成までは進めて、投稿は後で」という形は可能。その旨を伝える。
- **今回どの外部脳を使うか**を確認する（X アーカイブだけ / Evernote だけ / 両方）。

### 1. ネタの発掘（既存資産を流用）
`podcast-neta` スキルの手順 1〜3 と同じ要領で、外部脳からネタを発掘する。

1. **ツイートの機械的前処理**（X を使う場合）:

   ```bash
   python3 .claude/skills/podcast-neta/scripts/extract_tweets.py \
     --tweets twitter-archive/extracted/data/tweets.js \
     --account twitter-archive/extracted/data/account.js \
     --out tweet-drafts/.cache/tweets_candidates.json \
     --min-len 15
   ```

   出力件数（`kept`）を控える。ここはまだ意味的な選別はしていないことを伝える。

2. **意味的な選別**: 候補を約 250 件ずつのチャンクに分け、`podcast-idea-miner` を
   **並列起動**する（1メッセージに複数の Agent 呼び出しを並べる）。
   - 選別基準として [../podcast-neta/references/selection-criteria.md](../podcast-neta/references/selection-criteria.md) の全文を渡す。
   - Evernote を使う場合は `evernote` モードのマイナーを 1 つ追加する。
     テーマ種の例:「生き方 価値観」「後悔 挫折 転機」「こだわり 偏愛」「ものづくり 個人開発」。
   - マイナーは score 3 以上のネタを構造化 JSON で返す（捏造しない）。

> 発掘の詳細な運用は `podcast-neta/SKILL.md` を正とする。重複させず参照する。

### 2. 下書きへの整形（本体で実施）
発掘された各ネタ（`quote` / `why` / `angle` / `theme_hint`）を、
[references/tweet-criteria.md](references/tweet-criteria.md) の物差しに従って
**投稿できるツイート本文**に整形する。

- 元の引用の**主旨を保つ**。過去の自分の考えを、今の一人称で言い直す形にする。
  引用の意味を歪めたり、言っていない主張を足したりしない。
- 280 字以内。フック（1行目）→ 中身 → 余韻/問い、の流れを意識する。
- 1つのネタから**言い回し違いで最大2案**まで作ってよい（オーナーが選べるように）。
- ハッシュタグ・URL の付与方針は tweet-criteria.md に従う（付けすぎない）。

各下書きには、**必ず出典（元ツイートの日付 / Evernote ノート名）を併記**する。

### 3. 下書きファイルに書き出す
`tweet-drafts/YYYY-MM-DD.md`（日付は `date +%F`）に、次の構成で書く。

```markdown
# ツイート下書き — YYYY-MM-DD

## 1. <ひとことラベル>（テーマ: <theme_hint>）
- **下書きA**:
  > <ツイート本文（280字以内）>
  （xx字）
- **下書きB**（任意）:
  > <言い回し違い>
  （xx字）
- **出典**: > <元の引用>  （X, YYYY / Evernote「ノート名」）
- **狙い**: <このツイートで人格のどの側面が伝わるか。1文>
```

同じ日に複数回走らせる場合は上書き確認をする。
`tweet-drafts/` は個人的な引用を含む成果物なので `.gitignore` で丸ごと除外する
（`podcast-ideas/` と同じ扱い。手元には残るが Git 管理外）。

### 4. 本体チャットで数件だけ提案し、承認を仰ぐ
書き出したファイルパスと、**特に推したい下書きを 3 件だけ**本体チャットで見せる。
全件は貼らない（ファイルに任せる）。そのうえでオーナーに聞く:

> このうち投稿していいものはありますか？（番号で / 直したい所があれば直します）

- オーナーが番号を選ぶまで **`post_tweet` は絶対に呼ばない**。
- 「全部いい感じにやっといて」と言われても、投稿する具体的な文面と本数を
  一度確認してから投稿する（完全自動投稿はしない）。

### 5. 承認されたものだけ投稿する
オーナーが選んだ下書きだけを `mcp__twitter__post_tweet` で投稿する。

- 投稿前に、**実際に送る最終文面**をそのまま提示して最終確認を取る。
- 1回のやり取りで**一度に投稿するのは 1〜2 件まで**（連投しない）。
- 投稿後、返ってきたツイート URL / ID を本体チャットに残す。
- 下書きファイルの該当項目に「✅ 投稿済み（URL）」を追記して、二重投稿を防ぐ。

## 補足
- `twitter` MCP の `search_tweets` は直近しか取れない。過去の網羅分析は必ず
  ローカルアーカイブ（`extract_tweets.py`）を使う。
- 投稿は取り消しづらい外向きアクション。少しでも迷ったら投稿せず確認する。
- ネタは捏造しない。すべて実在する投稿/ノートの引用に紐づける。
