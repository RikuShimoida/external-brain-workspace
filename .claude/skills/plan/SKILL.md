## Issue 起点の実装計画

引数: `$ARGUMENTS`（Issue 番号。例: 19）

### 重要: このスキルの目的

このスキルは **Issue の内容から実装計画を立てる** ためのものである。
ブランチ作成・worktree 作成・コミット・PR 作成は一切行わない。**計画の提示のみ**が目的。
git の状態確認（`git status` / `git log` 等）も不要。

### 手順

1. **最初に必ず** `gh issue view $ARGUMENTS` を実行して Issue 内容を取得する。取得前に他の作業をしてはならない。
2. Issue を読み、対象（スクリプト / スキル / エージェント / ドキュメント / データソース）と期待動作を把握する。
3. 設計ドキュメントと照合し、影響範囲を特定する。
   - `CLAUDE.md`（データソース表・進め方の原則・スキル一覧・オーナーの人物像）
   - `docs/worktree-workflow.md`（開発フローに触る変更の場合）
   - `.claude/rules/`（git-workflow / command-rules）
   - 対象スキルの `SKILL.md` と `references/`
4. Issue で言及されているファイルが存在する場合、現在の実装を読んで問題点を確認する。
5. **横展開スキャン**: 今回の対象と同種の箇所が、他のスクリプト・スキル・ドキュメントに無いかを実装前に洗い出す。
   ここでは**実装も是非判断もしない**。「類似箇所がどこに何件あるか」を事実として把握するだけ。

   - **構文的横展開**: 同じ関数・同じ引数・同じ書式を grep して他ファイルの同種箇所を洗う。
     - 例: `scripts/line_parse.py` の日付処理を直すなら、`chatgpt_map.py` にも同じ処理が無いか見る
   - **意味的横展開**: Issue の「なぜやるのか」から本質的な課題を捉え直し、
     文字列が一致しなくても本来直すべき箇所を拾う。
     - 例: 目的が「地図を作ってから本文を取る2段構えに揃える」なら、
       まだ2段構えになっていない他のデータソースも同じ課題の一部として浮かび上がる

6. **並列可否の判定**（`/parallel` に投入されうるため、計画段階で明示する）。
   `docs/worktree-workflow.md` §2 に照らし、次に当たるなら「並列不可（直列）」と書く。
   - アーカイブ配下（`*-archive/`）や生成物ディレクトリを**書き換える**タスク
   - MCP への**書き込み**（`post_tweet` / `create_event` / `edit_note`）を含むタスク
   - 判断に迷う場合は推測せず、「このタスクはアーカイブや生成物を書き換えますか？」とオーナーに聞く。

7. 実行計画を、後述のフォーマットで表形式で提示する。

### 計画出力フォーマット

オーナーは散文を通読せず「気にした観点の表だけ」を拾い読みする。計画は**観点ごとの独立した表**で出す。
因果（根本原因）と設計判断の理由だけは、表に押し込むと読みにくいので短文で残す。

#### 1. 根本原因 / 背景

2〜3行の短文（表にしない）。

#### 2. 影響範囲

| ファイル | 変更内容 | 種別 |
|---|---|---|
| （パス） | （何を変えるか） | 新規 / 修正 / 削除 |

#### 3. リスク

| 項目 | 判定 | 備考 |
|---|---|---|
| 既存スキルへの影響 | 影響あり / なし / 要注意 | （波及先） |
| アーカイブ・生成物の書き換え | あり / なし | （どのディレクトリか） |
| 外部サービスへの書き込み | あり / なし | （あるなら要 承認） |
| 個人データの Git 混入 | あり / なし | （`.gitignore` 対象か） |

#### 4. 横展開

| 箇所 | 件数 | 扱い | 理由 |
|---|---|---|---|
| （ファイル） | （件数） | 今回スコープ / 別 Issue | （なぜそう扱うか） |

類似箇所が無ければ「横展開対象なし」と1行で明記する。

#### 5. 検証

| 対象 | 検証方法 | 何が言えれば OK か |
|---|---|---|
| （スクリプト / スキル / ドキュメント） | （dry-run → 実行 / パス実在確認 等） | （実測する数値・状態） |

#### 6. 並列可否

| 判定 | 理由 |
|---|---|
| 並列可 / 直列必須 | （共有資源に触るか） |

#### 7. 設計判断メモ（あれば）

「なぜこの方針か / なぜ別案を却下したか」を短文で残す。無ければ省略。

### 禁止事項

- Issue 取得前に git 操作やブランチ状態の確認を行うこと
- 「何をしますか？」と聞き返すこと（Issue に書いてある）
- ブランチ作成・worktree 作成・コミット・PR 作成などの実装作業

### 計画出力後の案内

計画を出したら、次のメッセージを提示して終了する。

```
計画を確認して、問題なければ /impl $ARGUMENTS で実装を始めてください。
直したいところがあれば言ってください。/plan $ARGUMENTS で計画を作り直します。
```
