# ポストモーテム記入スキル

オーナーは失敗をその場でボイスメモに吹き込み、Evernote のポストモーテム・テンプレに
文字起こしだけ貼った状態で放置する。このスキルはその**空欄を埋めてノートを更新する**。

狙いは、反省を気持ちで終わらせず **「次に同じ状況が来たとき自動的に失敗しない仕組み」** に
変換すること。中身の物差しは [references/postmortem-criteria.md](references/postmortem-criteria.md)。

## 大方針（CLAUDE.md と一致）

- **捏造しない。** ボイスメモに無い事実（時刻・金額・人物・心情）を作らない。
  分からない欄は空欄にせず **「要確認」＋確認したいこと** を書く。
- **記憶を外部化する。** 結論はチャットで流さず、必ずノート本体に書き込む。
- **説教しない。** 「気をつける」で終わる対策は無効。**意志ではなく環境を変える**対策にする。
- **一度に浴びせない。** 完了報告は要点2〜3個まで。全文をチャットに再掲しない。

## 手順

### 1. ノートを特定する

典型的な呼ばれ方は **`/postmortem <Evernote の URL>`**（URL だけ貼られることもある）。

- **渡された文字列から GUID（`8-4-4-4-12` 桁の16進、例 `a7f1baa8-4d87-49af-472a-b8cf97d5ebd3`）を
  抜き出し、それをそのまま `noteId` として `mcp__evernote__get_note` に渡す。**
  URL の形は問わない。Evernote は同じノートを複数の形式でリンクするが、**どれも GUID を含む**:
  - 共有リンク: `https://share.evernote.com/note/<GUID>`
  - アプリの「ノートリンクをコピー」: `https://www.evernote.com/shard/s◯◯/nl/<id>/<GUID>/`
  - 内部リンク: `evernote:///view/<id>/s◯◯/<GUID>/<GUID>/`
  - GUID が複数含まれる場合は**最初に現れたもの**を使い、`get_note` が失敗したら次を試す。
- GUID が見つからない／URL が無い場合は `search_notes` / `semantic_search` でノートを探し、
  **候補を出して確認する**（どのノートか勝手に決めない）。
- 取得したノートのタイトルを**必ず一言添えてから**作業に入る（別のノートを掴んでいないかの確認）。

### 2. 材料を読む

`get_note` の ENML から次を拾う。

- **ボイスメモ**セクションの文字起こし（＝一次情報。ここが唯一の事実ソース）。
- **使用したいケース / ケース例 / ポイント**（ノート上部）— 分析のレンズがここに書かれている。
- 埋めるべき **見出し 1〜9** と、その下の空要素。

**注意: ノート下部の「書き方例」には同じ見出し1〜9がサンプル入りで存在する。絶対に触らない。**
見分けは `--en-nodeId` の値。空欄側（上）だけを対象にする。

**文字起こしが無く音声ファイルだけの場合**（`structuredContent.resources` に audio がある）:
音声は読めないので、**Evernote 側で文字起こしを実行してもらうよう伝えて止まる**。
勝手に内容を想像して埋めない。

### 3. 中身を書く

[references/postmortem-criteria.md](references/postmortem-criteria.md) を Read して、それに沿って
1〜9 を書く。特に **5. 原因分析** では次の3レンズを必ず当てる（ノートの「ポイント」欄に対応）:

1. **3つ以上のことを同時にやろうとしてなかったか？**
2. **失敗種別は ADHD か？**（ADHD 起因なら対策は意志でなく仕組みへ）
3. **心得「自分を信用するな」で言うと何に違反していたか？**（自分の何を信用したのか）

材料が足りないレンズは **「要確認」** と書く。埋めた気にさせない。

### 4. ノートを更新する（ENML 編集の作法）

`mcp__evernote__edit_note` の **`mode:"replace"` を1回**で、見出し1〜9のブロックをまとめて
差し替える。9回に分けない（ノートのバージョン競合と取りこぼしを避けるため）。

- `find` は `get_note` の ENML から **バイト単位でそのままコピー**する。
  見出しの `style="--en-nodeId:xxxx;"` を**省略しない**。省略すると一致せず失敗する。
- `find` は「1. ケース の見出し」から「9. 付録 の閉じ `</ul>`」まで一続きで取る。
  空の `<ul><li><div><br/></div></li>…</ul>` はノート内に何度も出てくるので、
  **見出しごと含めないと ambiguous エラーになる**。
- `content` にも **同じ見出しタグ（nodeId 付き）をそのまま含めて**返す。見出しを消さない。
- `content` は well-formed XML。**`&` は `&amp;`、`<` は `&lt;`** に必ずエスケープする。
  ここが「not valid ENML」エラーの最頻出原因。
- 空欄の中身は `<div><br/></div>` だったり `<div><b><span style="--en-markholder:true;">…`
  だったりする。**実際の ENML を見てからコピーする**（決め打ちしない）。

書き込みは既存の空欄を埋めるだけなので事前確認は不要だが、
**既に中身が入っている欄を上書きする場合は、上書き前にオーナーに確認する。**

### 5. 報告する

チャットには**全文を再掲しない**。次の2〜3点だけ伝える。

1. 根本原因として何を置いたか（1〜2文）
2. 「要確認」として残した点（あれば）
3. アクションアイテムの見出しだけ

## 出力フォーマット（チャット）

```
「<ノートタイトル>」のポストモーテム 1〜9 を埋めました（書き方例はそのままです）。

**根本原因はこう置きました**
<1〜2文。心得「自分を信用するな」との対応も一言>

**要確認が<N>つ**
<埋められなかった点と、何を思い出せば埋まるか>

アクションアイテムは<N>つ（<見出しだけ列挙>）を未着手で置いてあります。
```

## 応用

- **仕事のインシデントにも同じ型を使う。** その場合 4. 影響範囲の「気分」を
  「他者への影響（迷惑・信用）」に読み替える（criteria 参照）。
- 同じパターンの失敗が繰り返されていると気づいたら、**9. 付録に関連ケースとして書き残す**。
  再発は最重要のシグナルなので、報告のときに一言添える。
