# データソースの詳細

[CLAUDE.md](../CLAUDE.md) にはソース一覧の表と安全警告だけを置き、詳細はこちらに集約する。
CLAUDE.md は毎ターン context に乗る固定費なので、**Read で足りるものは全部こちらへ出す**方針
（同じ考え方は [worktree-workflow.md](worktree-workflow.md) でも採っている）。

> **注意:** 探索の網羅性など「回答の質を直接左右するルール」は、このファイルではなく
> 各 `SKILL.md` 側にも書いてある。スキル実行時に必ずロードされる場所に置かないと、
> 読み飛ばされても**失敗が表面化しない**ため。二重化は意図的なもの。

## 全体の設計

`twitter-archive/` `chatgpt-archive/` `evernote-archive/` `line-archive/` `claude-log-archive/`
`kindle-archive/` `outputs-archive/` は個人データなので Git 管理外（`.gitignore` 済み）。

ローカルに落とすか、クラウドに置いたままかは、ソースごとに使い分ける。

| 方式 | ソース | 理由 |
|---|---|---|
| ローカルに落とす | X / ChatGPT / LINE / Claude Code ログ / Kindle | エクスポートが手作業 or 元ログが消える |
| クラウドに置いたまま | Evernote / Gmail / カレンダー / freee | 常に最新が読める。ディスクを圧迫しない |

大きいソースは **2段構え**（まず軽い「地図」を作り、濃いところだけ本文を取る）で扱う。
全展開すると容量とコンテキストの両方が破綻するため。

## X（Twitter）

- 実体: `twitter-archive/extracted/data/tweets.js`（約3,267件）
- ローカルファイルを直接パースする。

**重要:** 過去ツイートの網羅的な分析は Twitter MCP ではなくローカルアーカイブを使う。
MCP の `search_tweets` は直近しか取れないため。

投稿・検索の MCP（`post_tweet` / `search_tweets`）は別枠。投稿は承認制。

## Evernote

- 実体: ノート群（約8,463件）
- 「クラウドに置いたまま」が原則。ローカルに本文を落とさない
  （ディスクを圧迫せず、エクスポート作業なしで常に最新が読めるため）。

そのうえで、**取りこぼしを減らすために2つの入口を必ず両方使う**。

1. **キーワード検索**（全ノートが対象）… `semantic_search` / `search_notes` を
   テーマを変えて複数回投げる。全8,463件がそのまま母集団。
2. **地図から当たりをつける**（全ノートが対象）… `evernote-archive/note_map.tsv` に
   全ノートのメタデータ（作成日・更新日・ノートブック・タイトル・ノートID）だけを持つ。
   タイトル一覧を眺めて関連しそうなノートを選び、`get_note` で本文だけクラウドから取る。

**重要:** 2 は 1 の絞り込みではない。**独立した2本の経路**として走らせ、
両方の結果を合わせる。地図をフィルタとして使い、検索の母集団を狭めてはいけない。
目的は「なるべく多くのデータを参考にすること」。

地図は MCP 経由でしか作れない（Evernote は Python から叩けないため、他のソースのような
`scripts/*.py` は存在しない）。初回生成も更新も Claude が `search_notes` を叩いて行う。
更新は `updated:day-N` で差分だけ取り直せばよく、オーナーの手作業は不要。
全件の作り直しは重いので**サブエージェントに隔離**する。

## ChatGPT 過去会話

- 実体: `chatgpt-archive/`（全会話の索引 `conversation_map.tsv` 約4,540件
  ＋ 人生相談だけ抜き出した `lifetalk/` 60件）
- ローカルファイルを直接パースする。

ZIP を全展開せず、まず `scripts/chatgpt_map.py` で「地図」（日付・タイトル・メッセージ数だけの
一覧）を作り、`scripts/chatgpt_extract.py` で人生相談系の会話だけ本文を Markdown 化する。
価値観・悩み・家族の話が濃いソース。

## LINE トーク履歴

- 実体: `line-archive/`（7ルーム 約21,933件の地図 `talk_map.tsv`
  ＋ 濃い日だけ抜き出した `deep/` 39件）
- ローカルファイルを直接パースする（**MCP では取れない**）。

ChatGPT と同じ2段構え。`scripts/line_map.py` で「地図」（1日ぶんの件数・文字数だけの一覧）を作り、
`scripts/line_extract.py` でその日の最長メッセージが 300 字を超える日だけ本文を Markdown 化する。
合計文字数ではなく**最長メッセージ**で選ぶのは、長文が数件の日（仕組みの設計・相談）と
短文が大量に飛び交う日（友人との雑談）を分けるため。パースは `scripts/line_parse.py` に集約。

Evernote が「整理された結果」なのに対し、LINE には**家族に相談しながら仕組みを作っていく過程**が残る。
ただし**相手の発言が必ず含まれる**ので、Podcast / note / ツイートの素材にするときは
引用の扱いを他ソースより厳しくすること。

**重要:** LINE の個人トーク履歴は API では取れない（Messaging API はボット向け）。
取得はアプリからの手動エクスポート（`トーク設定 → トーク履歴を送信`）一択で、
ルームごとにオーナーの手作業が要る。

## Claude Code 過去ログ

- 実体: `claude-log-archive/`（136セッションの地図 `session_map.tsv`
  ＋ 濃いセッションだけ抜き出した `deep/` 40件）
- 元ログ `~/.claude/projects/` を読んで抽出（**リポジトリ外・30日で自動削除**）。

同じ2段構え。`scripts/claude_log_map.py` で「地図」（セッションごとのタイトル・発言数・
最長発言の一覧）を作り、`scripts/claude_log_extract.py` で**自筆の**最長発言が 100 字を超える
セッションだけ本文を Markdown 化する。パースは `scripts/claude_log_parse.py` に集約。

X / Evernote が「言葉の蓄積」なら、これは**手を動かしながらの思考**（なぜこう作ったか、
どこで迷ったか）。ただし元ログ 203MB のうち本人の発言は **868件・約8.2万字**
（抽出物にして 196KB＝元の 0.1%）しかなく、残りはツール出力と運用系レコードなので、
`type: "user"` でも `tool_result` / `isSidechain` / `isMeta` のものは必ず弾く。

**重要: 「本人が打った文字」と「本人が貼り付けた他人の文章」は同じ形で入る。**
どちらも `type: "user"` だから。実測では本人の発言 82,321字のうち **32,445字（39.4%）が貼り付け**
（VS Code のリリースノート等）で、しかも最長発言の上位を占める。長さだけで濃さを測ると、
貼り付けが1つあるだけでそのセッションが選ばれてしまう。そこで発言ごとに `kind` を付ける。

| kind | 手がかり（**1,000字以上の発言だけ**判定する） | 実測 |
|---|---|---|
| `pasted` | 日本語文字率が5%未満 / 話者ラベル `[Speaker N]:` が3回以上 | 4件・32,445字 |
| `template` | Markdown 見出しが10個以上 / 同じ長文が複数セッションに現れる（使い回し） | 2件・12,861字 |
| `self` | 上記以外（1,000字未満は無条件でこちら） | 846件 |

**捨てずに印を付けるだけにしてある。** 地図には `longest_self` `pasted` `template` の列が入り、
抽出物では発言の見出しに（貼り付け）（定型文）と付く。元ログは30日で消えるので、
判定を外して本人の長文を落とすほうが害が大きい（**迷ったら残す側に倒す**）。
`template` を `pasted` と分けるのは、要件定義テンプレートのように**本人が書いた定型文**は
他人の文章とは別物だから。どちらも濃さの物差し（`longest_self`）からは外すが、扱いは同じにしない。

### 消える前に取り切るための仕組み

**重要:** 元ログは `~/.claude/projects/` にあり、`cleanupPeriodDays` の既定
**30日で自動削除される**。参照方式では古いログが消えるため、抽出物をこちら側に持つ。
スクリプトは元ログを**読むだけ**で、書き換えも削除もしない。

X も Evernote も LINE も「取りに行けばいつでもある」が、**Claude Code のログだけは、
抽出を回さなかった期間がそのまま永久に失われる**。手で思い出して月1回叩く運用は成立しないので、
猶予を延ばす（下の①）のと自動で回す（②）のを両方かけてある。

#### ① 保持期間を30日 → 365日に延ばす

`~/.claude/settings.json`（**このリポジトリの外**・全プロジェクト共通の個人設定）に1行足す。

```json
{
  "cleanupPeriodDays": 365
}
```

- 2026-08-27 に設定済み。設定前は未設定＝既定30日だった。
- リポジトリ外なので、macOS を乗り換えたり設定を作り直したときは**ここを見て入れ直すこと**。
- ディスクは食う。設定時点で `~/.claude/projects/` は **349ファイル / 203MB**。1年ぶんなら数GB規模になりうる。

#### ② 抽出を自動で回す

`scripts/claude_log_sync.py` が定期実行の単一の口。地図 → 本文の順に走らせ、
最終実行日と前回からの差分を `claude-log-archive/last_run.json` に記録する。

```bash
python3 scripts/claude_log_sync.py            # 前回から24時間以内なら何もしない
python3 scripts/claude_log_sync.py --force    # 間隔を無視して必ず走らせる
```

発火の口は `.claude/settings.json` の **`SessionStart` フック**。このリポジトリで
Claude Code を起動すると走る。cron / launchd を選ばなかったのは、plist や crontab が
リポジトリ外に置かれると壊れても気づけないため。**仕組みごと Git に乗るほうを採った。**

安全装置が3つ入っている。いずれも「やめる」だけで、既存の抽出物には触らない。

| 安全装置 | 効くとき | 挙動 |
|---|---|---|
| worktree ガード | `.git` がファイル（＝ worktree）のとき | 即やめる。`/impl` `/parallel` の作業ツリーから発火してアーカイブを壊さないため |
| ロック | `claude-log-archive/.sync.lock` があるとき | 何もしない。1時間より古いロックは破る |
| 実行間隔ガード | 前回から24時間以内 | 何もしない（`--force` で無視） |

**このフックはこのリポジトリを開いたときしか走らない。** 30日開かないと穴が空くので、
①の365日がその保険になっている。片方だけでは成立しない。

#### 出力はどちらも「減らない」形にしてある

自動で回す以上、**元ログが消えた後に走っても過去の抽出物が減らない**ことが前提になる。

- **地図（`session_map.tsv`）はマージ書き込み。** `session` をキーに、今回スキャンできた行は
  最新で置き換え、**スキャンに現れなかった既存の行はそのまま残す**。
  素直に書き直すと、元ログが消えたセッションの行が地図から欠けていく。
  `last_seen` 列は「最後に元ログ側で実在を確認できた日」で、この日付が古い行は
  元ログがもう無く、地図と `deep/` だけが残っている行という意味になる。
- **`deep/` は上書きしかせず、選定外になったファイルを消さない。**
  **元ログが既に消えたセッションの抽出物もここに残っているため、一括削除してはいけない**
  （消えたログは二度と再生成できない）。判定の変更で古いファイルが残ったときは、
  元ログがまだあるものだけを選んで消す。

## Gmail

- 実体: 送信済み **1,213通 / 602スレッド**（2017年12月〜。受信箱は 166,476通あるがノイズが大半）
- Gmail MCP（`list_labels` / `search_threads` / `get_message`）。**読み取り専用で使う。**

Evernote と同じ「クラウドに置いたまま」型。ローカルに本文を落とさない
（第三者の個人情報・仕事の守秘情報を自分のディスクに数万件コピーしないため）。
他ソースのような `scripts/*.py` は存在しない。Gmail は Python から叩けず、MCP 経由でしか読めない。

**対象は原則「送信済みメール」に絞る。** 受信箱 166,476通に対し送信済みは 1,213通（約0.7%）で、
残りは案件の一斉送信・通知・広告が大半。送信済みだけが**自分が書いた言葉**であり、
他ソースと同じ「内側の言葉」として扱える。受信メールは必要なときにピンポイントで検索する。

**地図を作る必要はない。オーナーが手で育てたラベルがそのまま地図になる。**
`list_labels` で全ラベルの正確な件数が取れる。`案件メール/` 配下の10ラベル
（Java 8,020 / AWS 5,475 / React 2,870 など計 約23,876通）は案件の打診、
`転職` 6,814通はキャリアの動き、`サービス/` 配下は生活の記録にあたる。

**重要:** 件数は `list_labels` の値を使う。`search_threads` が返す `resultCountEstimate` は
**推定値で大きくズレる**（送信済み 602スレッドに対し 201 と返した）。件数を語るときは信用しない。
本文を取るときは `get_message` に `messageFormat: PLAIN_TEXT` を指定する
（HTML 本文で文脈を潰さないため）。

**重要:** Gmail MCP には書き込み系ツールが多数ある（`send_message` / `reply` / `forward` /
`create_draft` / `trash_message` / `label_thread` など）。**これらは使わない。**
外部への不可逆な送信・改変であり、オーナーの承認なしに触れてよいものではない。
読み取り3種（`list_labels` / `search_threads` / `get_message`）だけを使う。

X / Evernote / ChatGPT が「自分の内側の言葉」なのに対し、Gmail は**他者との接点**と
**時系列の事実**（いつ何が動いたか）の記録。ただし**全ソース中で最も機微度が高い**ので、
Podcast / note / ツイートの素材にするときは LINE よりさらに厳しく扱う。
相手の氏名・メールアドレス・社名・案件の条件は、そのまま成果物に出さないこと。

## Kindle ハイライト

- 実体: `kindle-archive/`（地図 `book_map.tsv` ＋ 1冊1ファイルの `books/`）
- 実測 **本棚43冊 → 線を引いていた35冊・766件・約6.0万字**（2026-08-26。取得失敗0件）

LINE と同じ「API が無いので手動エクスポート一択」型。`read.amazon.co.jp/notebook` を
ログイン済みのブラウザで開き、[kindle-export.md](kindle-export.md) の JS を DevTools に貼って
`highlights.json` を落とす。以降は `scripts/kindle_map.py`（地図）→
`scripts/kindle_extract.py`（1冊1 Markdown）→ `scripts/kindle_match.py`（`books` の索引と突き合わせ）。

**重要: ここでは濃さの閾値で間引かない。** 他ソースと違い、ハイライトは
**オーナーが読みながら既に選び終えた文**であり、こちらでさらに選別すると本人の選択を上書きしてしまう。

**Kindle の35冊と Evernote 由来の56冊はもともとほぼ別集合だった。** 重なりは **4冊だけ**で、
残り31冊・629件（全体の82%）が `books/index.md` の外にあった。
Kindle は技術書・実用書、Evernote の「読んできた本」は人生・仕事寄りという偏りの違いによる。

**Issue #35（2026-08-27）で、索引に載せる価値のある7冊を `volumes/` に起こした。**
選定は3段フィルタ（①`books` の趣旨に合うか → ②ハイライト25件以上か → ③既存索引でタグが手薄か）で、
件数の閾値だけでは決めていない。索引は相談のたび毎回ロードされる固定費なので、増やしすぎると発火精度が落ちる。
結果、`books` は63冊になり、突き合わせは **11冊 568件（74%）が索引内 / 24冊 198件が外**（`kindle_match.py` 実測）。
外に残した24冊は技術書・資格試験本（Clean Architecture / AWS認定 等）や数件しかハイライトが無い本が中心。
**捨てたわけではなく**、`books` スキルは索引に当たりが無いとき `kindle-archive/book_map.tsv` も見に行く。

**重要: このリポジトリは公開されている。** ハイライトは書籍本文の逐語引用なので
`kindle-archive/`（`.gitignore` 済み）の外に出さない。`books` の `volumes/*.md` は Git 管理下なので、
**本文を書かずポインタ1行だけ**を置く。Podcast / note / ツイートで使うときは引用の範囲に注意する。

Kindle for Mac のローカル DB（`AnnotationStorage`）は使えない。実際に開いたところ全32行のうち
`highlight` は1件だけで、しかも本文が空だった（2026-08-26 実測）。`My Clippings.txt` も
実機で読んだ本しか入らず、この Mac には無い。notebook 一択。

X / Evernote が「自分の言葉」なのに対し、Kindle は**他人の言葉に自分が反応した点**の記録。
`books` の `volumes/*.md` が「本が何を言ったか」なら、こちらは「**本人の琴線がどこで鳴ったか**」にあたる。

## 自分の生成物（既出ネタの地図）

- 実体: `outputs-archive/output_map.tsv`（`podcast-ideas/` `tweet-drafts/` `note-drafts/`
  `decisions/` の8ファイルから作った引用 **63件** の索引。2026-08-27 実測）
- `scripts/output_map.py` で作り直す。**毎回作り直してよい**（数十件しかないので差分管理は不要）。

**このリポジトリ自身も外部脳のひとつ**という位置づけ。他のソースが「過去に自分が言ったこと」なら、
こちらは**過去に自分（Claude）が提案したこと**の記録で、目的が2つある。

1. **重複回避**（`podcast` / `tweet` / `note`）… 同じネタを何度も提案する事故を防ぐ
2. **判断の一貫性**（`decision`）… 前と逆の推奨を黙って出さないようにする

```bash
python3 scripts/output_map.py                      # 地図を作り直す（既出の重複も stderr に出る）
python3 scripts/output_map.py --dry-run            # 書き込まず標準出力へ
python3 scripts/output_map.py --match "<引用本文>"  # この引用が既出かを問い合わせる
```

| 列 | 中身 |
|---|---|
| `kind` | `podcast` / `tweet` / `note` / `decision` |
| `file` `date` | どの生成物のどこから来たか |
| `label` | ネタのテーマ名（判断ログでは決定の題） |
| `status` | `posted`（X に投稿済み） / `draft` |
| `source` | 出典（`X, 2022-11` / `Evernote「ノート名」` など） |
| `key` | 正規化した引用の先頭24字（短い識別子） |
| `quote` | 引用本文 |

**重要: ツイート ID では突き合わせられない。** 生成物に ID が残っておらず、出典は
`（X, 2022-11）` のような年月表記だけ。過去8ファイルを遡って ID を振り直すこともできない。

**重要: 先頭一致でも足りない。** 同じツイートでも Podcast ネタでは要約されて
「スマート＝仕事ができるという認識が3年目まであった」、ツイート下書きでは逐語で
「スマートである＝仕事ができる という認識が社会人3年目くらいまではあった」と書かれる。
先頭も末尾もズレる。そこで**引用本文の文字 N-gram（8字）の重なり**で突き合わせている。
実測で、先頭一致では 0 組しか見つからなかった既出の重複が、この方式では **4 組**見つかった。

**重要: 拾えるのは「同じ引用」までで、「同じテーマ」は拾えない。** 別の引用で同じ話を
しているケースは機械では判定できないので、`label` 列を LLM が読んで判断する。
地図を作ってから濃いところを人が見る、という**2段構えは他のソースと同じ**。

**重要: 何を拾うかはアンカーで決めている。** `**出典**` `**根拠の投稿**` `**元の言葉**`
`（出典: …）` の4系統に紐づく引用だけを拾う。note 下書きの記事本文にも `>` の引用は出てくるが、
それは記事の一部であって既出ネタの出典ではないため、アンカー方式で切り分けている。
**生成物のフォーマットを変えるときは、このアンカーを残すこと。**

### かぶったときの扱い（オーナー決定・2026-08-27）

| 状況 | 扱い |
|---|---|
| `status` が `posted` | **除外する**（`tweet-draft` でのみ効く） |
| それ以外の既出 | **除外しない。別角度で出す** |

完全除外にしなかったのは、素材が有限（X の候補 1,051 件）で、除外し続けると早晩枯れるため。
Podcast も note も、同じ素材を別の角度で語り直すのはむしろ自然な使い方にあたる。
一方、投稿済みツイートと同じ趣旨をもう一度流すのは読み手に露骨にバレるので、そこだけ除外する。

再利用するときは、各生成物の **`既出` 欄**に「前回どの生成物でどう扱ったか」を残す。

## Google カレンダー

- 実体: 予定そのもの
- Google Calendar MCP（`list_events` / `search_events` / `create_event` など）。

予定の確認と登録に使う。**書き込む前に必ず内容を確認する。**
言葉ではなく**行動**の記録として、他ソースの裏取りに使える。

## freee（会計）

- 実体: 帳簿そのもの（売上・経費・仕訳・試算表）
- freee 公式のリモート MCP（`https://mcp.freee.co.jp/mcp`）。**読み取り専用で使う。**

Evernote / Gmail と同じ「クラウドに置いたまま」型。ローカルに帳簿を落とさない。
`scripts/*.py` は存在しない（Python から叩けず、MCP 経由でのみ読める）。

freee は 2026年3月に MCP サーバーを OSS 公開し、同月27日にリモート版を出した
（[freee/freee-mcp](https://github.com/freee/freee-mcp)）。**リモート版はローカル環境の構築も
freee アプリストアへのアプリ登録も不要**で、既存の Evernote MCP と同じ HTTP + OAuth で繋がる。
ローカル版（`npx freee-mcp configure`）はクライアント ID / シークレットの取得が要るので採らない。

**用途は税額シミュレーションと確定申告の準備。** 住宅ローン控除は所得税からの**税額控除**なので、
所得税額が控除可能額に届かないと枠が余る。「経費をどこまで積むか」「売上をいくら積むか」の逆算に
帳簿の実績値が要る。Evernote 側の「確定申告チェックリスト」「住宅ローン控除について」
「御殿場の家の価格とローン債務額」と突き合わせて使う。

**重要: 書き込み系ツールは一切使わない。** freee MCP は会計・人事労務・請求書など10サービス、
約270操作に対応し、**仕訳や取引の登録・更新・削除まで可能**。これらは使わない。
帳簿の破損は確定申告に直撃し、税務上の証憑性にも関わる。登録・修正はオーナーが freee の画面で行う。
Gmail（外部への不可逆な送信）と同種のリスクだが、**freee のほうが厳しく扱う**。

**重要: 許可するツール名はまだ確定していない。** Gmail のように読み取り3種を列挙したいが、
約270操作あり、接続して認証するまで正確なツール名が取れない。そのため現時点では
「書き込み系を使わない」という**原則だけ**を置いている。接続後に実ツール一覧を確認し、
使う読み取りツールを列挙してここへ書く（`parallel` / `plan` スキルの書き込みツール列挙にも反映する）。
**推測でツール名を書かないこと。** 存在しない名前がルールとして残ると嘘のドキュメントになる。

**重要: このリポジトリは公開されている。** 売上・所得・納税額・ローン残高などの具体的な金額を
Git 管理下のファイル（`docs/` `CLAUDE.md` `decisions/` 等）に書かない。数字は会話の中だけで扱うか、
Git 管理外に置く。Kindle ハイライトと同じ扱い。

未確認事項が2つある。接続後に実測して、この節を更新すること。

| 項目 | 内容 |
|---|---|
| 個人事業主プランの制限 | 部門マスタ等の一部エンドポイントが制限される可能性がある。試算表が取れるかは接続後に確認 |
| レート制限 | 1事業所あたり 120リクエスト/分（超過で 429）。通常の用途では問題にならない |

X / Evernote が「自分の言葉」、Gmail が「他者との接点」なら、freee は**数字で見た事実**の記録。
言い訳の効かない一次情報として、他ソースの裏取りに使える
（「稼ぎたい」と書いた年に実際いくら稼いだか、など）。
